**Bareiss and matrix representation.** The generated symmetric integer family is `M = 10^6 I + 10^6 J + E`, where `E_ij = hash(seed,min i j,max i j)%2001 - 1000`, seed 17. Off-diagonals are about 10^6 and diagonals about 2×10^6. It is dense and pseudo-randomly perturbed. For n≤245, `|xᵀEx| ≤ 1000 n ||x||²`, so this is mathematically SPD; that analytic argument is not asserted as a formal Lean theorem here. This is one family and one seed, not a statistical sample of all SPD matrices. Matrices are generated inside Lean from n and the seed, not supplied as trusted arrays. `Matrix.lean` consumes pairs of rows sequentially. The update is `(p*a_ij - a_ik*a_kj)/previousPivot`; the first divisor is 1. The timing predicates assume well-shaped generated matrices. Production checkers still need shape/symmetry validation, exact-division/soundness proofs and, for LDL, square and invertibility conditions.

**Concrete checker recommendations.**

1. Use `by decide +kernel` on a small Boolean acceptance proposition, with all expensive functions total and structurally recursive. Set explicit heartbeat and recursion limits. Avoid elaborator reduction as a throughput path; simple rfl sometimes works well but reflection through Nat.decEq has a different cost and stack behavior.
2. Represent dense symmetric matrices as upper-triangular lists and traverse paired rows sequentially. Avoid repeated flat-list indexing and mutation-oriented Array code in the trusted kernel computation. Use balanced trees only where access is genuinely nonsequential.
3. For H1, use exact Int Bareiss or an independently checked scaled-integer factorization, with a proved checker soundness theorem. Prefer external candidate generation plus kernel reconstruction only when that actually lowers total checked arithmetic. Prove shape/symmetry, positivity, exact divisibility, and the required invertibility conditions; Boolean acceptance alone is not yet a positive-definiteness theorem.
4. For H2/H3′, keep a proved common denominator or directed dyadic upper-bound invariant and reduce gcd frequency. Share continuation sums using dynamic programming. Chunk identities into separate checked declarations/modules and combine them with algebraic lemmas so one giant definitional reduction does not retain the full computation history. A nested recursive loop inside one theorem did not solve the measured memory growth.
5. Begin with one 25–50-sized full matrix or one ≤100-sized upper-triangle matrix per module. The measured full-50 group fits four workers in about 13 GiB aggregate RSS; upper-100 needs about 9 GiB per worker. Nat blocks of 10^4–10^5 iterations keep a single check around 1.5–2.4 GiB in these imports. Tune from measurements after introducing soundness lemmas and real input data. Do not place thousands of large checks in one module and assume caches are released between them.
6. Run at most four such modules concurrently initially, with one Lean worker each; increase only after checking aggregate RSS, and never exceed the task’s eight-process/64 GiB limits. This Lake needs `LEAN_NUM_THREADS=4 lake ... build ...`, not `lake build -j4`. Keep shared executable definitions in an already-built support module and independent certificates in leaf modules.

At the full-row n=100 rate, 7,962 matrices would take about 197.1 single-core hours per matrix family; upper storage at that size gives about 101.8 hours. “A few” matrices per case multiplies this again. These are explicit planning extrapolations from this artificial family. The uncompleted n=245 checks and significant cache growth make naive full-scale enumeration unsuitable as a certificate design commitment.
